# v10 network protocol: v10.0.2 vs v7.1.4, and the v10.0.3 shapes the official link speaks (§9)

Sources: the v10.0.2 bundle `~/jails/kru/src/Krunker_v10.0.3/deob/v10.0.2/game.js` (line numbers were taken from an identifier-renamed
copy with the same line layout, so `_N` names are not in the file) and the v7.1.4 reference at
`/home/user/jails/kru/src/Krunker_v7.1.4` (`packets.json`, `src/libs/io-client.js`,
`src/libs/ClientManager.js`, `src/index.js`, `src/data/game.js`). The bundle contains both the
client and the shared server simulation (`isServer` branches, `game.broadcast(...)`), so
server-to-client shapes can be read off the sender.

KrunkNative does not speak Krunker's wire format. It has its own numeric packet ids over knet
(`doc/transport.md`, `shared/include/shared.h` `NET_PACKET_*`). The wire ids below matter
only as names to map onto new `NET_PACKET_*` types, and for parity in the payload contents.

3** (`deob-10.0.3.js:111514`: `this.ahNum = add(this.ahNum, 3)` with `add` = `(a + b) & 255` at 27698,

These packets carry KrunkScript "entities" (archetypes defined in the map/script; see
krunkscript and map-format docs). Server limits come from config (19650-19660):

`onEntityDamage` (184304, 191471, 184966, 185323, 185861).

### Invite / Join

v10 has no party system. `copyInviteLink` copies `https://<host>/?game=<gameId>` (#inviteButton
"Copied URL" for 1250 ms); `openJoinWindow` joins a game link / code read from the clipboard, else
opens windows[23] (#gameURL + `joinGame()`); its parser takes `/?game=` / `/?party=` links and
`/^([A-Z]+):(\w+)$/` codes. The profile window's Friends tab joins with `openURL('/?game=<gid>', 1)`.
A game that needs a password: v10's server sends `ENTER_CODE` (popup `gameCode()`, `code` packet,
`UPDATE_CODE_TIMER`, `CODE_PASSED`); server_bin refuses the join (ERROR 004005) and the client shows
the same popup, then joins the same game again with the password in its JOIN packet (no countdown).

## 6. Port notes

- Implement: entity packets (with KrunkScript entities), `PLAYER_LOCKS`, the
  `SYNC_PLAYER` controlled-entity tail, `joinedRank` plus the ranked queue flow (against
  kn_brain, not FRVR), and optionally the event-bus friends/DM service in kn_brain.
- `CHEAT_CHECK` / `ccr` is a server-pushed code execution channel (XOR-obfuscated JS run through
  `eval`). KN's own protocol does not carry it. The official link answers it as the live client does:
  `client/src/net/krunker_cheat.c` decrypts it and evaluates it in a sandboxed QuickJS
  (`krunker_cheat_qjs.c`: fresh runtime, memory / time caps, no host APIs; the page's eval on the web build).
- `CHARGE_CONSENT_REQUEST/RESPONSE` is a server-initiated "spend currency?" confirmation
  (15 s timeout, guess: in-game KrunkScript purchases). Port it only if KrunkScript
  monetization is ported.
- `sdc` / `swu` / Discord / webpush / FRVR auth are live-service features. They map onto
  kn_brain endpoints if wanted; they are not gameplay.
- There is no version toggle (v10 only). HELLO / INIT keep their ruleset bytes for wire
  compatibility, carrying v10's ids only (`NET_HELLO_RULESETS`, `NET_INIT_RULESET`); nothing a
  client sends is refused for its version (§9.1 for the INIT the official link builds).

## 7. KrunkNative packet ids: the NET_PACKET_EXT envelope

Coordinator decision (2026-10-13): the 1-byte knet type stays. 250-253 are the Object Manager's
and 254 is `NET_PACKET_EXT`, an envelope whose payload is a little-endian u16 subtype followed
by the subtype's body (at most 510 bytes). Every packet added from v10.0.2 on is an EXT subtype.
It needs protocol 1.4 (`NET_PROTOCOL_MINOR` 4 = `NET_PROTOCOL_MINOR_EXT`): servers send EXT only
to peers whose HELLO announced 1.4, receivers ignore subtypes they don't know. Source of truth:
`shared/include/net_ext.h` (`NetExtSubtype`, `net_ext_pack` / `net_ext_unpack`).

## 8. Protocol 1.4.3 and 1.4.4: the flag uid, the zone object id (NetModeFlag, NetDomZoneState)

`NetModeFlag` (shared/include/shared.h) carries `int32 uid` (the flag's map object id, the index
NET_OBJECT packets use; v10's `ufl` uid) and `uint8 active` (ModeFlag.active: in play for this
mode). It is in NET_PACKET_MODE_STATE (40, a flag list of 8 entries) and NET_PACKET_FLAG (44). The
packets have no version field of their own: NET_PROTOCOL_PATCH 3 marks the layout (HELLO / INIT
patch). A 1.4.2 peer reads the old layout, so a KN client and server must come from one build.
The server takes the uid from the flag's raw map record (Object.raw, the same record the mode
loader reads), not from the record's position, and the official-server link (client/src/net/krunker_link.c)
sends its own v10 uids with active set.

Protocol 1.4.4 (NET_PROTOCOL_PATCH 4): `NetDomZoneState` (NET_PACKET_DOM_UPDATE, 142) carries `int32 object_id`,
the zone's map object id, read from the zone's raw map record like the flag's. The zone's `uid` stays the
dom_zones index the client mirrors. The same rules apply: the packet has no version field, and a KN client and
server must come from one build. The bridge (`net-bridge/v10Translate.ts`) sends `uct` with each zone's object id as
v10's uid (`updateDomZone` matches the zone by uid, `v10.js` 188544).

Protocol 1.4.6 (NET_PROTOCOL_PATCH 6): `NetSkinsPacketV2` (NET_PACKET_SKINS, 35, 40 bytes) carries the paint of each worn
skin after the uid and the three store indices: `PlayerSkinPaints` (primary, secondary, melee), each a `SkinPaint` {int32 color
0xRRGGBB or -1, int32 shader number or -1}. The server sends it only to a peer that announced patch 6
(`net_peer_has_skin_paint`, shared/src/net.c); a peer on an older patch gets the 16-byte `NetSkinsPacket` (V1) it reads today,
and every reader takes both sizes (`net_packet_read_skins`), so bots (which send V1 to everyone) and pre-patch servers still
work. The paint is the owner's first painted copy of each index (doc/v10/paint-copy.md). The native client applies it to the
player's weapon and melee skin meshes (`skin_fx_apply_paint`). The bridge's C side (server/bridge) announces patch 6 and
accepts both sizes; the TypeScript v10 bridge still announces 1.4.5 patch 5 and gets V1.

Protocol 1.4.5 (NET_PROTOCOL_PATCH 5): `NetStatePacket` (NET_PACKET_STATE, 6, the per-tick player state) carries the
values the v10 "k" record needs and the state did not have: `float step_val` (player.step_val, v10 stepVal), `uint8
on_ground`, `uint8 grapple_active` with `float grapple[3]` (player.grapple.point), and `float ping`. The server fills
them from the player (shared/src/net.c net_packet_from_player) and the client applies them (net_packet_apply_player,
from client_apply_state). The state packet grew from 57 to 79 bytes; unlike patches 3 and 4 the two sizes are both
read: `net_packet_read_state` takes the 57-byte V1 (its tail at rest, on_ground 1) and the 79-byte V2, and a server
sends V1 to a peer that announced patch < 5 (`net_peer_has_state_v2`, like SPAWN / RECON for WP-C). A client that only
took the 79-byte form dropped every STATE of a 1.4.4 server: the other players stood at their spawn with frozen legs.
The remote walk cycle is the v10 rule (v10.js:169517): `player_update` lerps the carried step value between
consecutive STATEs (`step_carried`, posBuffer 's') and fires the step sound at each zero crossing (posStep); a V1
STATE keeps the distance-driven cycle. The bridge (`net-bridge/v10Translate.ts`) maps the record field by field
(`v10.js` 191557 sender; 220285 handler); the native official-server link (`client/src/net/krunker_link.c`) fills
the tail from the record's [6] stepVal, [7] onGround, [11] grapple and [12] ping.
